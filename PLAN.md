# PLAN.md

Staged build-out for the Fluent CSS framework. Stages are meant to be tackled roughly in order, but each is self-contained — pick one up whenever you're ready. Conventions and design rules live in [CLAUDE.md](CLAUDE.md); this file is just the sequencing.

## Stage 0 — Project setup ✅
- [x] Decide and add tooling: package.json, a minimal build step (e.g. concatenate + minify `src/` into `dist/`), and a local dev server for `public/index.html`. — PostCSS (`postcss-import` + `postcss-preset-env` + `cssnano`) with `build`/`build:min`/`watch:css`/`serve`/`dev` npm scripts.
- [x] Scaffold the `src/tokens/`, `src/base/`, `src/components/`, `src/utilities/` folders per CLAUDE.md. — each with placeholder files and an `index.css` entry point.
- [x] Wire `public/index.html` to load the built (or source) CSS so it's a live demo page from day one. — loads `../dist/fluent.css`, served via `npm run serve`/`dev`.

## Stage 8 — Theming & customization ✅
- [x] Document how consumers override `--accent` and other tokens to rebrand. — new `README.md` (theming, dark/light override, RTL sections).
- [x] Verify light/dark theme switching works via both `prefers-color-scheme` and a manual class/attribute toggle. — Added System/Force-light/Force-dark/Toggle-RTL buttons to `public/index.html` for live human testing. Fixed the one real gap this surfaced: `src/tokens/elevation.css`'s shadows (flagged back in Stage 1 as deferred here) now roughly double their alpha under dark theme — light-theme alpha values were nearly invisible against an already-dark surface.
- [x] RTL support pass (logical properties instead of left/right where feasible). — Audited every component + base file for physical `left`/`right`/`inset`/`margin-left`/`padding-left`/`text-align:left` and converted to logical equivalents (`inset-inline-*`, `padding-inline-*`, `margin-inline-start`, `text-align: start`, `border-*-start-radius`) in checkbox/radio/switch (hidden-input overlay), select (chevron + padding), panel (dock side + corners), nav (active-link underline + actions alignment), tabs (active underline), menu (dropdown alignment + item text), table, and base list indentation. `translateX()` effects (switch thumb, panel slide) aren't direction-aware on their own, so both got an explicit `:dir(rtl)` flip.

Three real bugs found and fixed while verifying, not just cosmetic — the last one only surfaced after the user noticed the panel had started opening on the wrong side in plain default LTR:
1. **Build pipeline was silently defeating the RTL fix.** `postcss-preset-env`'s `logical-properties-and-values` and `dir-pseudo-class` features were statically rewriting `inset-inline-*`/`:dir(rtl)` into fixed LTR-only physical values/selectors at build time (confirmed via direct inspection of the compiled CSS — the logical properties never survived the build). Disabled both features in `postcss.config.js` with an explanatory comment, since target browsers support both natively and a build-time "polyfill" for an inherently runtime-dependent concept just bakes in the wrong answer.
2. **A genuine `<dialog>`-specific browser bug: logical inset/border-radius properties aren't reliably resolved on `<dialog>` at all**, in either direction — not just "stuck as LTR" under RTL as first assumed. Confirmed with a controlled A/B test: an identical `inset-inline-end` on a plain `<div>` flips correctly under `dir="rtl"`; on `<dialog>` it doesn't reliably resolve either way. The postcss polyfill disabled in fix #1 had been accidentally masking this for LTR by hardcoding a physical `right: 0` — removing the polyfill exposed it, and the panel started opening on the left even in default LTR (this is what the user caught). Fixed properly by not trusting logical properties on this element at all: `panel.css` now uses explicit physical `right`/`left`/`border-*-radius` for the LTR base case, with an explicit `:dir(rtl)` override flipping them, verified with `getBoundingClientRect()` in both directions (not just a screenshot, since the transition/`@starting-style` interaction made a couple of earlier screenshot-only checks misleading — see next point).
3. **Testing-methodology trap, worth remembering:** reading computed styles or taking a screenshot immediately after calling `showModal()` can catch the panel mid-`@starting-style` transition, producing readings that look like a position bug but are just a timing artifact. Fixed by either disabling `transition`/`transform` for a settled-state measurement, or confirming the visual end-state with a real screenshot after the transition has had time to run.

Verified end-to-end: full-page headless-Chrome screenshots with `data-theme="dark"` forced (confirmed shadow visibility fix and no contrast regressions anywhere) and with `dir="rtl"` forced (confirmed checkbox/radio/switch mirror to the right, select chevron flips left, nav actions/tabs/breadcrumb/card-footer buttons reorder correctly). The panel was re-verified in both directions via `getBoundingClientRect()` after fix #2 — right-docked in default LTR, left-docked under `dir="rtl"` — and confirmed visually against the real `public/index.html` (not just an isolated test file).

## Stage 10 — Distribution & QA ✅
- [x] Minified build output + source maps. — Found and fixed a real bug: `--map` had silently produced *no* sourcemap at all (not even inline) since the project moved to a `postcss.config.js` file, because `postcss-load-config` passes the CLI's `--map` option nested as `ctx.options.map`, but postcss itself expects `map` at the top level of what the config exports — a plain-object config export can't forward it. - [x] npm packaging (package.json `main`/`exports`, versioning). — Added `main`/`style`/`exports` (`.` → `dist/fluent.css`, `./min` → `dist/fluent.min.css`, `./src/*`), a `files` allowlist (`dist`, `src`, `README.md` — needed since `.gitignore` excludes `dist/`, which `npm pack` would otherwise inherit and wrongly omit the actual deliverable), and bumped to `0.1.0`. - [x] Cross-browser check (backdrop-filter fallback, focus-visible support, etc.). — Added a "Browser support" section to `README.md` listing every modern-CSS feature used (`color-mix()`, `:has()`, `mask-image`, `backdrop-filter`, `@starting-style`/`allow-discrete`, `:dir()`, logical properties, native `<dialog>`) with approximate support baselines, and is explicit that **only Chromium was actually tested** in this environment (no real display was available for Safari; confirmed by `screencapture` failing with "could not create image from display") — this is disclosed rather than glossed over. - [x] Accessibility pass: color contrast, keyboard navigation, reduced-motion behavior. — See below.

**Accessibility pass — real bugs found via actual WCAG-formula computation, not eyeballing:**
1. `--color-neutral-foreground-3` (light theme) measured 2.64:1 against `bg-1`, under the 3:1 floor even for large text/UI components. Changed `#a19f9d` → `#8a8a8a` (~3.45:1).
2. `--accent`/`--accent-hover`/`--accent-pressed` used directly as *text* color (links, nav active state, breadcrumb hover) measured only 3.64/4.38/2.47:1 against the dark-theme page background — all under 4.5:1 (accent-pressed particularly badly, since darkening — the right move for light-theme "more emphasis" — makes dark-background contrast worse, not better). Root cause: those tokens are tuned for use as a *fill* paired with white text, not as text color themselves. Fixed by adding new theme-aware `--color-link`/`--color-link-hover`/`--color-link-active` tokens (`src/tokens/colors.css`) — light theme reuses the existing accent tokens as-is (already 4.5:1+), dark theme gets independently-tuned lighter values (4.82/5.48/6.25:1). Updated `src/base/typography.css` (`a`/`a:hover`/`a:active`), `nav.css` (active link), and `breadcrumb.css` (hover) to use them. Decorative, non-text uses of `--accent` (underline bars, borders, the spinner) were left alone — those are subject to the more lenient 3:1 non-text threshold, which they already pass.
3. **Bigger structural finding:** the colored badge variants (`--brand`/`--success`/`--warning`/`--danger`) — a tinted-pill design (semantic color as text, ~15%-tint-into-background as the pill fill) — failed WCAG AA almost everywhere: light theme ranged 3.71–4.32:1 (all under 4.5:1) and dark theme 2.71–3.16:1 (badly under), and no amount of adjusting the tint percentage could fix dark theme, because these hues are simply too dark to work as text on an already-dark background regardless of how the pill background is mixed. Fixed by switching those four variants to a solid background with white text (matching the pattern `.fluent-alert__icon` already used) — white text on each solid hue measures 4.53–5.37:1 in both themes with no per-theme tuning needed. The neutral/default badge variant was unaffected (verified separately) and keeps its original tinted-pill look, since its base color already flips light/dark per theme. Re-verified visually (not just numerically) that the redesigned badges still look good in both themes.
4. **Keyboard navigation:** structural audit (not just spot-checking) — grepped the whole demo page for `onclick` on anything other than a real `<button>`/`<a>` (none found) and for the interactive ARIA roles in use (`alert`, `list`, `status`, `switch`, `tab`/`tablist`, `tooltip` — no custom `menu`/`menuitem` roles, matching the simpler disclosure-widget pattern actually used). Every interactive component is built on a real native focusable element, so keyboard operability is structural, not something layered on afterward. Documented one known simplification: tabs and menu items are each independently `Tab`-focusable rather than implementing the full ARIA APG roving-`tabindex` + arrow-key pattern.
5. **Reduced motion:** re-confirmed (not re-litigated) that every `transition`/`animation` in `src/components/` either uses the `--duration-*` tokens (which collapse under `prefers-reduced-motion` per `src/tokens/motion.css`) or is one of the two deliberately-standalone exceptions from Stage 6 (`.fluent-spinner`, exempt on purpose since its motion *is* the information; `.fluent-skeleton`, which does respect it).

All fixes verified end-to-end: rebuilt clean, re-ran the WCAG contrast computation confirming every previously-failing pair now passes, and visually re-verified the redesigned badges and new link colors in both themes via headless-Chrome screenshots.

## Stage 11 — Section background gradients ✅
- [x] Reusable gradient utility for section backgrounds. — `src/utilities/gradients.css` (`.fluent-gradient`, the first file in the previously-empty utilities layer), following the same variant pattern as `.fluent-badge`/`.fluent-alert`: a single `--gradient-color` custom property drives every stop, so a `--variant` only overrides that one value. Five variants: default (neutral) plus `--brand`/`--success`/`--warning`/`--danger`, mirroring `.fluent-badge`'s variant set. Stops derive from existing tokens (`--accent`, `--color-success/warning/danger`, `--color-neutral-bg-1`) rather than new hardcoded colors, so rebranding via `--accent` keeps working. First pass used a flat two-stop `linear-gradient()`; a second pass tried a multi-blob look (four soft `radial-gradient()`s of the same hue) but that read as patchy rather than fluid — visible oval silhouettes where each blob's fixed-size fade ended inside the box. Settled on a single seamless diagonal `linear-gradient()` (close-value stops, so the transition reads as smooth light-to-slightly-deeper tone rather than a visible band) plus one soft corner highlight via `radial-gradient(circle at 12% 8%, ...)` left at its default "farthest-corner" size so its fade-to-transparent edge lands exactly at the box's far corner, never inside it — the fix for the patchiness, and the actual reason the Windows 11 look reads as smooth ambient light rather than a spotlight.
- [x] Demo the gradients with dummy cards. — New "Gradients" section in `public/index.html` (added to the sidebar's existing "Surfaces" group, right after Card), one swatch per variant, each a `.fluent-gradient` container hosting the existing static + interactive dummy `.fluent-card` examples so cards visibly float above any variant.

Verified: `build`/`build:min` both clean; grepped `dist/fluent.css`/`dist/fluent.min.css` to confirm the new rules made it through the previously-unexercised utilities import chain. Visually verified all 5 variants across all three iterations via headless-Chrome screenshots in light theme and forced dark theme (`data-theme="dark"`), compared directly against a reference screenshot of the real Windows 11 setup screen: the final version reads as one seamless diagonal wash with a soft ambient highlight in both themes (no patch/blob edges anywhere), cards stay legible with visible border/shadow separation, and `--warning`/`--danger` (the highest-risk hues) stay clean rather than muddy in dark mode — no dark-mode override block was needed, since every ingredient color is already theme-aware or theme-stable, the same reasoning `.fluent-alert`'s tint already relies on. No text sits directly on a gradient anywhere in the new section (each swatch is labeled by a `.fluent-hint` caption placed above the gradient box, not on top of it).

## Stage 12 — Button groups ✅
- [x] Bootstrap-style joined button row. — `src/components/button-group.css` (`.fluent-btn-group`), the first "joined row" pattern in this codebase (nav/tabs/menu all just use plain flex + gap between separate items). No new class needed on individual buttons: `.fluent-btn-group > .fluent-btn` positional selectors (`:first-child`/`:last-child`/implicit middle) zero the inner corners and collapse adjacent 1px borders into one via `margin-inline-start: -1px`, matching the codebase's existing preference for structural selectors over positional modifier classes (`breadcrumb.css`'s `li:not(:last-child)::after`, `list.css`'s `:last-child`). `isolation: isolate` on the group contains the hover/focus/active `z-index: 1` bump (needed so a hovered/focused button's edge isn't visually covered by its flush, later-painting neighbor) to the group's own stacking context. Outer corners use logical `border-start-start-radius`/`border-end-start-radius`/`border-start-end-radius`/`border-end-end-radius` — the first use of the logical corner-radius longhands specifically in this codebase (as opposed to `inset-inline-*`/`margin-inline-*` elsewhere), notable because `panel.css` documents a real Chrome bug in this exact property family failing to resolve under RTL, though only on `<dialog>` elements.
- [x] Demo. — New "Button groups" section in `public/index.html` (sidebar's "Form controls" group, right after Buttons): a plain `role="group"` toolbar-style group (Left/Middle/Right, all `--secondary`) and a segmented-toggle-style group mixing `--primary` (active) with `--secondary` plus `aria-pressed` (Day/Week/Month), showing variant styling still applies per-button inside a group.

Verified: `build`/`build:min` both clean; grepped `dist/fluent.css`/`dist/fluent.min.css` to confirm `.fluent-btn-group` rules compiled in. Visually verified via headless-Chrome screenshots in light theme, forced dark theme, and forced `dir="rtl"`: borders read as a single 1px line between buttons with no doubling or gap, only the true outer corners are rounded, and — the one real risk flagged going in, given the `panel.css` precedent — the rounded corners correctly land on the new visual outer edges under RTL (confirmed by close-up crop: the group's DOM order stays fixed while the visual order mirrors, and the radius follows the mirrored edges correctly, not the physical LTR ones).
